How a parent signs in

Signing in and being allowed are two different things, and Lanternina keeps them in two different places. This page explains the mechanism, the pieces it is made of, and the alternatives that were considered and set aside.

01 Three questions that are usually confused

Most of the difficulty here comes from treating one problem as three, or three problems as one. Lanternina answers them separately, in three different places, and that separation is the design.

Who are you?

Authentication. Answered by Microsoft Entra External ID. It checks an email and a password and hands back a signed statement. It knows nothing about Lanternina.

Is that statement genuine?

Token validation. Answered by the API, in panel/tokens.py. It checks the signature, the issuer, the audience and the expiry. It has no opinion about whether you may proceed.

May you proceed?

Authorisation. Answered by the account gate, in shared/accounts.py. A record in our own database says pending, active, rejected or suspended. Only active passes.

Why not let Entra answer all three. It can answer the first two. It cannot hold a sign-up open for days while a human decides — a directory records that an account exists, not that a person has looked at it and agreed. Keeping the third answer in our own database costs one more lookup per request and buys a decision we control.

Why an application needs a scope pointed at itself

The panel is one application playing two roles: the page in the browser is the client, and the API in the container is the resource. OAuth has no notion of "the same app", so the resource role has to be named before the client role can ask for a token addressed to it.

That is what Expose an API does. Without it, MSAL can only obtain a token for Microsoft Graph or an ID token, and neither is addressed to our API. An ID token is a statement about who signed in, meant for the client that requested it; using one as an access token is a common and quiet mistake, because it often works right up until an audience check is added.

Two directories, on purpose

The Azure subscription is administered from a workforce tenant. Parents live in a separate External ID directory. The same human being can hold an identity in both, and they remain unrelated accounts.

What this buys: if the panel is ever compromised, whoever is inside has nothing at all towards the Azure subscription — no resources, no data tier, no billing.

What it costs: two places to look when something is wrong, and an administrator who cannot test the parent experience with the account they already have.

Why the gate is a dependency and not middleware

Middleware runs before routing, so it has to be told which paths to skip, and that list is a place to forget an entry. A dependency is the opposite shape: a route is unprotected only if someone wrote it that way, and the protection is visible in the signature.

Cost: the dependency has to be repeated per route rather than declared once. Buys: forgetting it is visible in the file you are reading, not in a configuration list somewhere else.

One detail cost an hour and is worth recording: with from __future__ import annotations, FastAPI resolves annotations by name against module scope. A dependency defined inside a factory function is unresolvable, and FastAPI silently treats the parameter as a query string instead — answering 422 to every authenticated request. The dependency therefore sits at module scope.

04 What happens when a parent signs in

Eleven exchanges, none of which carry a password to us. The parent's password is seen only by Entra.

and sends only its hash P->>E: redirected to the user flow, with the hash E-->>P: sign-up or sign-in page P->>E: email and password E-->>P: back to app.lanternina.com with a short-lived code P->>E: the code, plus the original verifier E-->>P: access token, signed with RS256 P->>A: GET /api/me, Authorization: Bearer … A->>E: public signing keys, fetched once and cached A->>A: signature, issuer, audience, expiry A->>A: account lookup, and the gate A-->>P: 200 with the account, or 403
Step 3 and 7 — why the code is exchanged with a verifier (PKCE)

A page running in a browser cannot keep a secret. Anything shipped to the browser is readable by whoever holds the browser, so the classic "client secret" is not available to us.

PKCE replaces the secret with something generated fresh for each sign-in. MSAL invents a random string, sends only its SHA-256 hash when starting, and presents the original string when redeeming the code. An attacker who steals the code from the redirect cannot use it, because they do not have the string that hashes to what Entra recorded.

Limit: PKCE protects the code in transit. It does not protect a token already sitting in the browser. That is why tokens are short-lived, and why the gate is checked again on every request rather than once at sign-in.

Step 10 — where the public keys come from, and why not from a URL we wrote

The token is signed with a private key that only Entra holds. To check the signature the API needs the matching public key, which Entra publishes at a JWKS endpoint.

The API does not hold that address as a constant. It reads the OIDC discovery document at the configured authority and takes both issuer and jwks_uri from it. The reason is in the next section: the issuer for this tenant is not what the authority URL suggests, and a template would have produced a value that looks plausible and rejects every real token.

Cost: one HTTPS request the first time, then a cache with a five-minute lifetime. If the discovery document cannot be read, the panel refuses rather than guessing.

Every one of those refusals returns the same message. An endpoint that explains which check failed is an oracle: an attacker fixes one field at a time until it stops complaining.

Read the issuer, do not derive it. Measured from the discovery document on 7 August 2026. The authority we configure is https://lantessveb.ciamlogin.com/lantessveb.onmicrosoft.com/v2.0, and the issuer it reports back is https://79825125-….ciamlogin.com/79825125-…/v2.0 — the subdomain is the tenant id, not lantessveb. Nobody would derive that from the authority URL, and the same substitution happened on the previous directory, so it is the rule rather than an accident.

This is why TokenVerifier.from_authority reads the issuer out of the discovery document instead of composing it. The one place the value could have been hard-coded is the one place it would have been wrong.

The same tenant also answers at login.microsoftonline.com, and there it reports a different issuer. A front end pointed at that address would receive tokens that look entirely valid and would be refused by our API, producing a 401 that reads like a credentials problem and is a wrong URL in a configuration file.
Why the algorithm is pinned, and how we know the pinning is what refuses the forgery

A JWT states, in its own header, which algorithm was used to sign it. A verifier that honours that statement can be attacked: the public key is public, so an attacker can switch the header to HS256, sign with the public key as a shared secret, and present a token that verifies.

The API therefore passes algorithms=["RS256"] rather than trusting the header.

The test for this was wrong at first, and it is worth recording why. The original test forged an HS256 token signed with the public key in PEM form. It passed — but measuring showed PyJWT has its own guard that refuses PEM keys as HMAC secrets, on decode as well as encode. The same forgery was refused even with the algorithm list left wide open. The test proved the forgery failed; it did not prove our pinning is what failed it.

The replacement isolates the pinning: a genuinely valid HS256 token, signed with exactly the key the resolver returns, and not in PEM form so the library guard stays out of the way. Widening the algorithm list makes the permissive version accept sub=attacker; ours refuses.

06 The gate — where a valid token still gets nothing

A parent who completes sign-up has an account in the directory and no account in Lanternina. The two are created at different moments, by different parties, and only the second one grants anything.

Written as an allowlist. The check is "status must be active", not "status must not be one of the blocked ones". A status added in a year's time is then refused by default instead of quietly granted. Two tests hold that shape: one parametrised over the enum, so new members are covered without anyone remembering, and one that simulates a status nobody has invented yet.
The bootstrap, and why it is guarded on "nobody is active" rather than on a flag

The gate creates a problem the moment it exists: the first parent lands in pending, and there is no administrator yet to approve them. Wiring authentication without solving this locks the owner out of their own system.

One configured address self-activates, and only while no account is active yet. Once anyone is in, the setting is inert — even if it is left in place. That guard was chosen over "remember to remove the variable" because someone will not remember.

It runs as a separate recorded decision rather than a special case inside register, so the store keeps its promise that signing up never produces an active account, and decided_by = bootstrap stays in the record permanently.

Verified by removing the guard: without it, a second caller at the same address is admitted with 200. With it, 403.

Why a pending account costs nothing

Generating content calls paid models. A pending account generates nothing, so it calls nothing, so it costs nothing. The gate is therefore also the cost control, which is why it sits before any route rather than inside each one.

This ties to the budget alerts already deployed at 50, 80 and 100 per cent of a monthly figure set at deployment time.

What the account record holds

Subject, contact address, status, the timestamp and author of the decision, and a free-text note. Household is an opaque identifier.

What it deliberately does not hold. Nothing about the learner — no name, no age, no diagnosis, no history. The authentication layer knows there is a household and does not know who is in it. That is not privacy applied afterwards; it is the reason the record has the shape it has.
What is not stored anywhere

Passwords — never seen. Tokens — never written down; they are checked and discarded within the request. Signing keys — only the public half, cached in memory for five minutes.

The consequence is worth stating plainly: a full read of our database yields a list of email addresses and their approval status, and nothing that would let anyone sign in.

Why the administrator has no route to the data, and why that was chosen

Measured on the deployed account: publicNetworkAccess disabled, disableLocalAuth true, and exactly one data-plane role assignment — held by the runtime identity, not by the administrator. Two independent locks, either of which alone would be enough.

Buys: a stolen administrator credential reaches no family's data. Costs: approving the second parent needs a job running inside the network, which is not built yet. The cost is visible and the alternative — opening the firewall to a laptop — would not have been.

08 What was chosen, and what was set aside

Each row is a fork that was actually open. The reason for not taking a branch matters more than the branch itself, because the reason is what tells you when to revisit it.

QuestionTakenSet aside, and why
Where does approval live? Our database Inside Entra. A custom authentication extension can block a sign-up, but synchronously — it implements an allowlist, not a queue a human works through. And directory contents do not survive a tenant move.
How does the front end prove identity? Bearer token, validated by us The Static Web App's built-in auth. Less code: the platform would do the whole dance and pass a header. But then the API's security rests entirely on the linked-backend restriction holding. Validating the token means the rule lives in code, not in a portal setting someone can change without seeing the consequence.
Which authority? ciamlogin.com login.microsoftonline.com. It answers, and issues tokens, with a different issuer. Not a preference — a wrong answer that fails late.
How is the client secured? PKCE A client secret. Not available: a single-page application cannot hold one. Anything shipped to a browser is readable.
Does the parent see a consent screen? No — pre-authorised Letting consent happen. It would work. But the person arriving here is a parent trying to review activities, and the first thing in front of them should not be a dialog listing OAuth scopes.
Which claim carries identity? sub Email. An address can be changed, reassigned, or claimed by someone else. sub is opaque and stable. Email is kept only as something to show the person deciding on an account.
Domain in front of the app DNS only Proxying through Cloudflare. The static web app renews its certificate by resolving to itself over the public internet. A proxy answers with its own addresses, and the failure is not an error today — it is a certificate that stops renewing in about three months.
The one that is still genuinely open: session lifetime

An access token lasts about an hour. What happens after that hour is not yet decided.

Silent renewal keeps the parent signed in and means a stolen refresh token is useful for longer. Signing in again is safer and is friction in a system whose whole point is that a parent stays involved without being worn down.

This is a product decision more than a technical one, and it has not been made. Nothing in the code assumes either answer yet.

09 The four portal steps, decoded

Each of these had to be done by hand because everything inside a directory is tenant-scoped and outside the reach of the deployment template. Here is what each one actually changed.

STEP 1  App registration, platform "Single-page application", redirect https://app.lanternina.com

Created the identity of the application and the list of addresses Entra will send a person back to. Choosing the SPA platform rather than "Web" is what makes Entra require PKCE and refuse to issue tokens against a client secret.

Why two redirect addresses are registered, not one

Redirect addresses are matched exactly, character for character, and are case-sensitive on the path. Both https://app.lanternina.com and the generated Static Web App hostname are registered, because Entra accepts several on one registration and there is no cost to holding both.

The benefit is that the front end can be exercised on the generated hostname before DNS and the certificate are in place, without a second trip through the portal afterwards.

STEP 2  Expose an API · api://e80af2eb-… · scope access_as_parent

Declared the resource role. Before this, there was nothing for a token to be addressed to. This is what makes the aud claim in the eventual token point at us, which is the claim the API compares literally.

STEP 3  API permissions, then admin consent

Recorded that the client role intends to ask for that scope, and that an administrator has agreed in advance on behalf of everyone in the directory.

Why "My APIs" was empty and "APIs my organization uses" was not

The first tab filters to applications the signed-in user owns; the second lists every service principal in the directory that exposes an API. Creating an app in a CIAM tenant does not always record the creator as an owner, which is enough to empty the first list while the second one works.

Nothing was broken. The two tabs answer different questions and only one of them was the question being asked.

STEP 4  User flow panel-signup-signin, with Email among the attributes, attached to the app

Chose what a parent actually sees, and what comes back in the token. Email was included because the panel shows it to whoever decides on an account — without it, an account arrives with nothing to look at.

The extra step, and the reason it is not cosmetic

Adding the application to its own Authorized client applications list tells Entra the API trusts this client, and the consent screen is skipped. Thirty seconds now, and one obstacle permanently removed from the path of every parent who ever signs up.

Every branch here ends in a refusal or a reduced service. None ends in a guess.
