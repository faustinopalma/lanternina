The claims in a token, spelled out

A token is a list of three-letter names. Each one is an abbreviation of an ordinary word, and the words are more general than the situation we are using them in. This page writes them out in full, says where each name is defined, and marks the ones nobody has ever spelled out officially.

01 Why the names are three letters, and not words

A token travels in an HTTP header — Authorization: Bearer eyJ… — on every single request, and headers have size limits that servers enforce. Every character in every claim name is paid for again on each call. Writing subject instead of sub costs four bytes per request, which is nothing once and is not nothing a million times a day. Compactness is a stated goal of the JWT format, and short names are its direct consequence.

The harder question is not why they are short. It is why they are those words.

iss, sub and aud are not authentication vocabulary. They are the vocabulary of any signed assertion: a notary, a subject, a recipient. The triad is older than JWT — SAML spelled the same three out in XML as Issuer, Subject and AudienceRestriction.

Why the obvious words would be wrong. It is tempting to read sub as "user" and aud as "resource". Both readings break on real cases.

sub is not always a user: in the client-credentials flow, where one service calls another with no person involved, the subject is an application. And aud is not always a resource: in an ID token — the one that tells the front end who signed in — the audience is the client itself. Same claim, opposite role.

The generic names are not obscurity for its own sake. They are correct in cases where the specific names would lie.

02 The seven names registered by RFC 7519

The JWT specification registers exactly seven claim names. Everything else in a token comes from a later layer — OpenID Connect, or the identity provider's own vocabulary.

ClaimIn fullWhat it assertsDo we use it
ississuer The principal that issued the token. Microsoft: identifies the security token service and the tenant of the authenticated user. In v2.0 tokens the URI ends in /v2.0. checked
subsubject The principal the token is about. Immutable. See §04 — it behaves in a way that is easy to get wrong. checked
audaudience The recipients the token is intended for. A party that does not find itself listed must reject the token — the specification words this as an obligation on the reader, not as a label on the token. checked
expexpiration time The time after which the token must not be accepted. Microsoft notes a resource may also reject it earlier. checked
nbfnot before The time before which the token must not be processed. Guards against a token minted for later use. not required
iatissued at Microsoft's own wording is narrower than the name: "specifies when the authentication for this token occurred". checked
jtiJWT ID A unique identifier for the token, for replay detection. Entra does not emit it — it emits uti instead, described in its own documentation as "equivalent to jti in the JWT specification". not emitted

Note what is absent from this list: azp and scp. Neither is part of RFC 7519, which is why they feel like a different kind of word. They are.

03 What Entra adds, written out

The column on the right is the honest part. Some of these abbreviations are expanded in an official document; others are universally read a certain way without anyone having written it down. Marking the difference costs a column and prevents a confident wrong answer later.

scpscope "The set of scopes exposed by the application for which the client application has requested (and received) consent." Space-separated. Included only for user tokens. not spelled out

04 The four that matter to us, and one surprise

Read as a sentence, the token we expect says: this person authenticated; this client acts for them; within this permission; at this door.

sub — the parent

The key our account store is built on. Immutable, and never reassigned.

azp — the front end

The application that asked for the token on the parent's behalf. Not the same thing as the parent.

scp — access_as_parent

What that client may do in the parent's name. Declared by us when we exposed the API.

aud — the panel

Who the token is addressed to. In v2.0 tokens, always the client ID of the API.

The surprise: sub is not a user id. Microsoft's documentation states that the subject is "a pairwise identifier that's unique to a particular application ID. If a single user signs into two different applications using two different client IDs, those applications receive two different values for the subject claim."

So the same parent, signing into a hypothetical second application in the same directory, would arrive there under a different sub. The two applications cannot correlate her by comparing that field. For a project whose rules say personal data stays local and nothing about her leaves the device unnecessarily, that is a property worth keeping rather than working around.

The consequence to remember: sub is the right key for us, and it is the wrong key to hand to anyone else, because outside our application it means nothing. If we ever need an identifier that is stable across applications in the tenant, that is oid, and it is a different privacy trade — it is exactly what lets applications correlate a person.
Why azpacr = 0 is the correct value and not a weakness

The value records how the client authenticated: 0 public client, 1 client secret, 2 certificate. Our front end runs in the parent's browser, where any secret we shipped would be readable by anyone who opens the developer tools. A secret visible to everyone is not a secret, so Entra classifies a single-page application as a public client and refuses to issue it one.

That is what the Single-page application platform choice declares at registration, and it is why PKCE is required rather than optional. The client is not authenticated; it is identified, and the only thing binding it to something real is the list of registered redirect addresses. That is the reason that list is kept short and exact.

05 Claims that look useful and are not

Three of these carry an explicit warning in Microsoft's own reference. They are the ones most likely to be reached for by someone writing an authorisation check in a hurry.

ClaimWhy it is temptingWhy it must not decide anything
name Human-readable, and right there. "The value can vary, it's mutable, and is for display purposes only. Don't use this value to make authorization decisions."
preferred_username Looks like an account name; often an email address. "Since this value is mutable, don't use it to make authorization decisions." An email address can be reassigned; a subject cannot.
aio, rh Present in every token, so they look meaningful. Internal to Entra, opaque, and documented as claims "resources shouldn't use".
The shape of the mistake. All three fail the same way: they work perfectly in testing, because in testing the name and the email never change. They fail the first time a parent changes her email address — and they fail open or closed unpredictably, depending on which record changed first. An identifier used for a decision has to be immutable, and only sub and oid are.

06 What the panel checks today, and what it does not

From panel/tokens.py, the verifier requires five claims to be present and validates issuer and audience against configured values:

audience=self._audiences,
options={"require": ["exp", "iat", "iss", "aud", "sub"]},
ClaimStatusNote
issrequired and comparedRead from the discovery document, never derived from the authority URL.
audrequired and comparedCompared literally against the configured value.
exp, iatrequiredExpiry enforced by the library.
subrequiredThen used as the key for the account lookup, which is a separate decision.
scpnot checkedSee below. Harmless today, a real gap the moment a second scope exists.
azpnot checkedOnly one client exists. Checking it would add nothing that aud does not already give.
nbfnot requiredPresent in practice; not demanded.
The gap, stated plainly. Microsoft's reference says of scp: "The application should verify that these scopes are valid ones exposed by the application, and make authorization decisions based on the value of these scopes." We do not.

With a single scope in existence the omission changes no outcome — any token addressed to us carries access_as_parent and nothing else. It becomes a defect the day a second scope is added and someone assumes it separates permissions. It will not, until something reads it.
Two questions, two answers. Everything above establishes who is knocking. Whether the door opens is decided afterwards, by the account gate, from a record in our own database. A token can be perfectly valid and still be refused, and that is the intended behaviour rather than a rough edge.
