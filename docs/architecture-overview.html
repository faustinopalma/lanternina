Lanternina

A home system that offers activities to adolescents across cognitive profiles, with a parent steering. Interests, difficulty, reading support and content variety are explicit settings. Content is generated in the cloud and printed on paper; handwriting is read back by a scanner. Nothing reaches the adolescent that a parent has not approved.

01 What it is, and the two things it will not do

A system like this can easily end up optimising for engagement. This one does not, and the refusal is structural rather than aspirational — it is encoded in the types, the tests and the deployment.

The parent is the point

Not a bottleneck to be automated away. No feature is built whose value is "the parent no longer has to think about this". Agents may only propose; there is no field anywhere in which an agent can record that its own output is acceptable.

Nothing is a judgement about her

No score, no grade, no progress trend, no ability estimate — not in types, storage, prompts, logs or UI. Vision output describes ink on paper ("cell 3 is empty"), never what that means about her.

Never built, including as an intermediate step: streaks, daily goals, variable reward schedules, leaderboards, notifications triggered by inactivity, engagement metrics of any kind — and, on the vision side, facial recognition, face or person detection, emotion or attention inference, gaze estimation, biometrics. Enforced by tests/test_boundaries.py, which fails the build if vision/ so much as references them.
Stopping is a legitimate outcome. Every flow can be abandoned at any point, with no penalty and no follow-up prompt. SessionOutcome.ABANDONED is a normal value, not a failure.
Variety is chosen, not inferred. Lanternina can rotate topics and formats frequently for an adolescent who wants novelty, or keep a familiar structure. It never derives that choice from speed, errors, stopping, presumed boredom or attention.

02 The shape

Three zones. The parent can be anywhere; the learner's data never leaves the house; the loop that actually reaches her is made of paper.

Two names are used from here on, because the device and the cloud stopped being precise once both grew parts. Lanternina Hub is the machine in the house: sealing keys, ledger, camera, and the link to the display. Lanternina Cloud is the Azure tier: the parent dashboard, the stored themes and approvals, and the single door to the models.

Read the arrows into the house. There are none. The device opens every connection itself, outbound. No open ports, no port forwarding, no tunnel that lets anything dial in — the same reason Azure Arc and IoT Edge were both rejected earlier: an inbound control channel to a device in a minor's home is a liability whatever protocol it uses.
A dashboard write stops at storage. Adding content, approving it or changing configuration does not call a model, enqueue work, notify the house or schedule anything. The server in the home starts work only when its own local logic chooses to make a request.

03 Who can approve content for a child

The answer shapes the rest of the design: the cloud tier is deliberately given less authority than it could have.

The cloud records and displays. The device decides. The parent taps approve in the cloud, but the cloud can only record an intention. The seal that makes an item deliverable is minted on the mini-PC, with a key that never leaves the house. Consequence: even the operator of the service cannot approve content for your child.

Why the coordinates are normalised

Cells are defined as 0–1 over the quadrilateral of the markers' inner corners, so their positions are independent of paper size, printer margins, camera distance and DPI. If the generator and the reader ever disagreed on the geometry, answers would be attributed to the wrong questions — a failure that looks like data rather than a bug. The QR carries the spec version, and a sheet the reader does not understand is refused, not guessed at.

Degradation is honest

Without the cloud, only checkbox-like cells are attempted; everything else is marked needs_review and the reading is flagged degraded. The system prefers "the parent should look at this" to a confident wrong answer. A smiley drawn outside every declared cell is invisible to the pipeline — correct behaviour, and now a known design property.

Known and unfixed: the ink threshold is badly centred. INK_PRESENT = 0.04 against a lightest real mark of 0.045 — about 8 % headroom, calibrated on one sheet, one pen, one scanner. The proposal is to move ambiguity into needs review, which routes to the parent: the correct direction to fail in.

05 The cloud tier, as deployed

20 resources across three resource groups, entirely from Bicep. Counted with az resource list on 7 August 2026; the numbers below are that count, not an estimate.

Resource groupHoldsCountLifetime
…-coreVNet, private DNS zones, Log Analytics, Container Registry, two managed identities9Long. Survives app redeploys.
…-dataCosmos DB serverless, storage queue, private endpoints7Longest — deleting it loses households
…-appContainer Apps environment, worker, Static Web App4Disposable. Safe to delete and recreate.

Azure adds a fourth group of its own, ME_cae-…, holding the infrastructure behind the Container Apps environment. It is created and deleted by the platform, not by our template.

Resource groups are split by lifetime, not by layer, so that redeploying the application never puts the data at risk.

No keys, anywhere

Cosmos has disableLocalAuth: true; the storage account has allowSharedKeyAccess: false; the registry has no admin user. Everything authenticates with a managed identity. Cosmos keys in particular cannot be scoped down, so a leaked one is total — which is why there are none.

The data tier is private

Cosmos and the queue are publicNetworkAccess=Disabled, reachable only through private endpoints from inside the Container Apps environment. The compute tier stays publicly reachable — that is the product. Partition key is the household id, so tenant isolation is structural rather than a WHERE clause somebody eventually forgets.

Two apps, because they answer to different signals. api scales on HTTP: a request to a zero-scaled app triggers activation and is served. worker scales on the queue, for content generation, vision reads and safety checks that genuinely take tens of seconds. Putting a queue in front of an interactive API would not make it faster — it would make it asynchronous.

06 What crosses the boundary

The list is short on purpose, and it is the claim the whole design exists to be able to make.

leaves the device

  • content-generation prompts
  • rectified page crops

That is the entire list.

never leaves the device

  • her name, her profile, her interests as an identified person
  • the sealing keys
  • the approval ledger
  • scans and session records
  • the mapping from an opaque household id to a real person
Treated as data, never as instructions: text recognised from her handwriting, free text the parent types, anything decoded from a QR code. A worksheet is a piece of paper that a model reads — anyone who can put text on a page can attempt prompt injection, so recognised text is never concatenated into an instruction position.
A rule that also has a second, unrelated reason. The sheet preview is streamed through our own endpoint rather than handed to the browser as a storage URL. That keeps the storage account private and lets us apply a content security policy — an SVG can carry a <script>, and the strings inside ours come from a model and from parent-typed text.

07 Decisions, and what they cost

Recorded here rather than discovered later. A design that only documents its happy path is not documentation.

Work begins on a request from the house

The dashboard persists state and returns. It never wakes compute on behalf of the device. The server in the home decides when to ask for something; the frequency and decision rule are intentionally still open.

Cold start is machine-facing latency. API and worker can both be at zero. The home server keeps its request open while Container Apps activates and the cloud computes. No parent or adolescent is waiting on that request, so the interface does not need a spinner, a completion notification or a follow-up prompt.

Container Apps HTTP ingress has a documented 240 second timeout. Longer work uses a correlation id and durable result. If the request expires, the home server waits according to its local policy and contacts the API again. Completion still does not call the house or notify a person.

One origin for queued work. If the implementation uses the queue, a message may be created only while handling an authenticated home-server request. Dashboard routes do not receive dispatch authority.
