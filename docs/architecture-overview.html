Lanternina

Lanternina offers activities to adolescents with a parent steering. The hub controls paper, scanning, displays and the clock. The container calls the models. The parent approves the initial activity; later pages and continuations are generated and screened without another parent review.

01 What it is, and the two things it will not do

A system like this can easily end up optimising for engagement. This one does not, and the refusal is structural rather than aspirational — it is encoded in the types, the tests and the deployment.

The parent is the point

Not a bottleneck to be automated away. No decision is taken on the parent's behalf — convenience is allowed, delegation is not. Agents may only propose; there is no field anywhere in which an agent can record that its own output is acceptable.

A profile is kept, and it is never shown

The system stores page observations and activity outcomes. It computes a profile over recent evidence and sends its prose to generation and continuation. The panel does not expose it as a score. Block-list checks reject named ways of revealing adaptation; they do not prove that every generated sentence respects that boundary.

Never built, including as an intermediate step: streaks, daily goals, variable reward schedules, leaderboards, notifications triggered by inactivity, engagement metrics of any kind — and, on the vision side, facial recognition, face or person detection, emotion or attention inference from images, gaze estimation, biometrics. Enforced by tests/test_boundaries.py, which fails the build if vision/ so much as references them.
Stopping is a legitimate outcome. Every flow can be abandoned at any point, with no penalty and no follow-up prompt. SessionOutcome.ABANDONED is a normal value, not a failure.
The memory includes configuration, generated material, reported activity duration and endings, reading-derived summaries and profile observations. The raw reading contract blocks implicit copy and pickle, but an explicit HTTP dictionary can be retained. Administrator development retention defaults off, permits writes for 14 days and gives each admitted reading its own 14-day lifetime.

02 The shape

The hub sends household material and page images to the container. The container holds the model clients and household stores. No model runs in the house.

The hub controls the scanner, printer, display files and clock. The container stores parent decisions and returns documents, images and readings through replies to hub requests.

Read the arrows into the house. There are none. The device opens every connection itself, outbound. Settings and approval writes store state for the next hub request. Model-assisted brief editing is a separate browser path. Neither operation opens a connection to the house.

03 Who can approve content for a child

The answer shapes the rest of the design: the cloud tier is deliberately given less authority than it could have.

The panel stores a parent decision on an offered activity. The hub retrieves approved documents over authenticated HTTPS and decides when to start. This path trusts the container's selection; it does not use the older Proposal delivery seals.

Why nothing on the page is for a machine

The design this replaced put four ArUco markers and a QR code on every sheet, and defined cells as 0–1 coordinates over the markers' inner corners — so that the generator and the reader could not disagree about geometry. It worked: marker sides measured 176–178 px against 177.2 expected at 300 dpi, and 13 of 13 cells read correctly. The cost was that every page had to be laid out by something that could also describe itself, which is why they all looked like forms. It is in attic/.

Degradation is honest

Reading is a model's job and there is no reader underneath it: no cloud, no reading, and a page that comes back while the panel is unreachable waits. Anything the model did not answer for, or answered for with something outside what was asked, is marked needs_review. The system prefers "the parent should look at this" to a confident wrong answer.

05 The cloud tier, as deployed

20 resources across three resource groups, entirely from Bicep. Counted with az resource list on 7 August 2026; the numbers below are that count, not an estimate.

Resource groupHoldsCountLifetime
…-coreVNet, private DNS zones, Log Analytics, Container Registry, two managed identities9Long. Survives app redeploys.
…-dataCosmos DB serverless, storage queue, private endpoints7Longest — deleting it loses households
…-appContainer Apps environment, worker, Static Web App4Disposable. Safe to delete and recreate.

Azure adds a fourth group of its own, ME_cae-…, holding the infrastructure behind the Container Apps environment. It is created and deleted by the platform, not by our template.

Resource groups are split by lifetime, not by layer, so that redeploying the application never puts the data at risk.

No keys, anywhere

Cosmos has disableLocalAuth: true; the storage account has allowSharedKeyAccess: false; the registry has no admin user. Everything authenticates with a managed identity. Cosmos keys in particular cannot be scoped down, so a leaked one is total — which is why there are none.

The data tier is private

Cosmos and the queue are publicNetworkAccess=Disabled, reachable only through private endpoints from inside the Container Apps environment. The compute tier stays publicly reachable — that is the product. Partition key is the household id, so tenant isolation is structural rather than a WHERE clause somebody eventually forgets.

The activity, drawing, reading and continuation paths execute in the API process. A worker or queue described in infrastructure is not evidence that these calls use it. Long requests can fail at ingress; a durable correlation-and-result protocol is not implemented for this activity path.

06 What crosses the boundary

This list used to be short, and being short was the claim the whole design existed to make. It stopped being the claim on 23 August 2026: the cloud tier is in the EU and holds personal material on the same terms as the house. Saying so plainly is better than a boundary that quietly moved.

leaves the house

  • generation prompts containing household settings, recent activity history, profile prose and the current reading when continuing
  • a page off the glass, together with the blank it was printed from
  • household memory, including observations and reported activity outcomes
  • photographs from the handheld camera, once it exists

controlled in the house

  • equipment operations and display files
  • the clock and current run snapshot

Activity approval is stored in the container's household store. The current installation's credentials were not inspected in this revision.

A complete plain-language view of household memory is not built. The parent can clear activity memory and profile observations; deleting the generated trail is a separate operation. These routes do not establish complete tenant-wide erasure.
Treated as data, never as instructions: text recognised from handwriting, free text the parent types, anything decoded from a QR code. A worksheet is a piece of paper that a model reads — anyone who can put text on a page can attempt prompt injection, so recognised text is never concatenated into an instruction position.
A rule that also has a second, unrelated reason. The sheet preview is streamed through our own endpoint rather than handed to the browser as a storage URL. That keeps the storage account private and lets us apply a content security policy — an SVG can carry a <script>, and the strings inside ours come from a model and from parent-typed text.

07 Decisions, and what they cost

Recorded here rather than discovered later. A design that only documents its happy path is not documentation.

Work begins on a request from the house

The hub checks rhythm, work already running, the approved backlog and the daily limit. Browser-assisted brief editing can call a model, but cannot start equipment in the house.

Cold start adds latency to the hub's request. A scan or continuation can have somebody waiting at the equipment, so this latency can be visible. Current replica configuration was not checked in this session.

The historical ingress budget used here is 240 seconds. A timeout can lose the activity response. A durable result protocol would be additional work, not an existing recovery guarantee.

One origin for queued work. If the implementation uses the queue, a message may be created only while handling an authenticated home-server request. Dashboard routes do not receive dispatch authority.
