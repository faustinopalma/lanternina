# Activity record and clock

The parent asked for 24-hour times throughout the panel, deletion of individual historical activities, a step-by-step view of the current activity, and two checks of the record-clearing operation before using it again. The earlier deletion incident selected a household's documents from the shared container and removed settings as well as history.

## Time display

The shared time input now accepts `HH:MM`, from `00:00` through `23:59`. A text input with an HTML validation pattern makes the format independent of the browser's native time picker; it costs the native picker and its hour/minute controls. The Rhythm and running-activity deadline forms use this input. Localized timestamps, the household clock and the hub camera gallery explicitly use `hourCycle: "h23"`. Their existing timezone selection remains unchanged.

## Current activity

The hub reports its current run files after processing endings and before the schedule checks, and again after starting an activity. The device-key route stores one snapshot per household. The authenticated panel reads the snapshot and opens each current activity's chronological record. The status gives the current heading, the wait start and any explicit ending time requested by the parent. The trace shows recorded events; it does not prove that every physical action has completed.

The existing hub timer runs every 60 seconds. The visible panel refreshes every 30 seconds and on focus. These intervals are configuration values, not a measured delivery guarantee: long-running work and network failures can delay reporting. The panel labels a snapshot older than 180 seconds as the last known state. This chosen threshold tolerates missed updates but leaves up to three minutes in which an old state can look current. A missing snapshot is unavailable, not idle. An unreadable run file is reported explicitly. Historical deletion remains available when a stale snapshot still names a run.

## Deletion scope

Both deletion routes derive the household from the authenticated account. Single deletion also selects the requested run ID. The Cosmos store checks the dedicated `trail` container identity, supplies the household partition key and parameterized predicates, materializes the complete candidate list, and validates each candidate before the first delete. Only `trail` and `made` documents qualify. Each write deletes one document by ID and household partition. No container or partition deletion API is used.

The snapshot has type `progress` and survives both operations. Settings, approved activities and other households survive. Single deletion leaves other runs untouched. The UI requires a confirmation and allows cancellation; bulk deletion also invalidates any displayed current trace so deleted steps do not remain visible.

These operations remove activity-log documents. They do not stop a running activity or delete the separate returned-material, observation and blob stores. An operation interrupted during point deletes can leave some selected rows in place; repeating it is supported. A running hub can write new rows after deletion. There is no tombstone, cross-store purge or migration of legacy records still in `sources`.

## Approved multiday lifecycle

The owner chose to keep an activity open until its path concludes or the parent explicitly terminates it. The owner also chose a configurable limit on open activities. The implementation uses a default of one open activity and accepts integers from one through ten; these are implementation choices, not measured participation thresholds. One prevents a second approved activity from starting while the first is unanswered. A larger limit permits concurrent activities and requires the parent to disambiguate photographs when several returns are possible.

A waiting run no longer expires at its nominal duration or at midnight. Its stored moment, sheet pointers and return instructions survive for later days. The existing daily start ceiling remains independent from the open-activity limit. Lowering the limit leaves existing runs intact and prevents new starts until the count falls below it. The runner enforces the cap under its existing activity lock, before device output. Unreadable run files remain visible and count towards the cap until the parent terminates them.

The activity log offers a separate, confirmed termination command for each run. The command remains queued while the hub is offline. The UI shows a request awaiting the hub rather than claiming immediate termination. Replaying an acknowledged or delayed command cannot terminate another run. The proposal view also uses the hub's run identifiers and snapshot instead of assuming the nominal duration defines whether an activity is open. Its end-by and close-now controls address that one run. End-by and close-now retain the planned-ending path and its existing 30-minute allowance; termination removes the live run directly. History deletion remains a separate action and never terminates an activity.

The main timer still refreshes the chosen days, hours and timezone before admitting new work. It saves that rhythm for the photograph and reminder workers. Outside allowed activity hours, an open run stays open and an exact-target photograph remains queued without a continuation call. Processing resumes during allowed hours. A failed rhythm fetch writes a no-days fallback, pausing this processing until a later successful refresh. The saved rhythm has no independent freshness timer, and a continuation already claimed before the end of the band can finish afterward.

Reminders apply only to the most recently entered waiting step, within allowed hours and on the local date when that step began. A received photograph suppresses further reminders for that step. Waiting across a date boundary does not replay them. Existing within-day help offsets remain unchanged; this change does not resolve the separate mismatch between nominal work time and very early return reminders observed above.

## Photographs and the current record

The camera freezes the eligible run, moment and waiting timestamp when it accepts a photograph. Camera selection and capture time are checked before ambiguity. A unique target can continue that exact step. Several targets produce an awaiting-assignment state and no model call; the parent chooses from the frozen candidates that still match an open step. A stale target, a later step or a different family's activity cannot receive the photograph through that choice. Scanner input is not guessed between multiple open activities.

The assignment queue uses one deterministic command identifier per photograph. Creating the message rather than upserting it prevents concurrent requests from replacing an existing choice. The hub synchronizes the authoritative photo state before acknowledging the command; a failed synchronization leaves the request pending. The panel shows pending requests after refresh and the actual assigned run when the photo record contains one. Processing details remain available separately. A failed processing attempt is retained without automatic replay, because a partial attempt may already have produced a physical output.

The current record says when the last successful hand-over was reported and whether the step still awaits a response or has received a photo. A drawn image alone is not labelled printed. A photo received while the step remains open is not labelled completed. Plans, continuation documents and model assessments remain available in collapsed technical details, with their meaning distinguished from observed activity. Their timestamps are labelled as filing times. The stored completion summary still contains elapsed calendar minutes for diagnostics, but its model-facing material omits that duration because waiting time is not measured participation.

Explicit early closing now files its actual output event, and a successful return files its collect event. Automatic help and way-out display messages still lack archived events. Event delivery remains best effort, without a durable event outbox: an offline hub can perform a termination without successfully filing its event. The interface is a view of reported events and last-known state, not a complete physical audit.
