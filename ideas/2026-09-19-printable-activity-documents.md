# Printable activity documents

The production release on 19 September 2026 integrated Astra, native Typst documents and role-aware application entry. The release and its remaining acceptance work are recorded under [Production release](#production-release-on-19-september-2026). The earlier sections retain the planning and laboratory evidence. Independent language settings remain unimplemented.

## Observation and scope

On 19 September 2026, the owner reported a comprehension trial of the printed sheets. The sheets work reasonably well as activity material, but they lack a separate, plainly written explanation of what to do. This is a reported observation, not a measured comparison between renderers. The requested result is a coherent document of one or two pages, with generated illustrations and shapes, composed layout, and actual PDF text written by a language model. The explanation must be concise, clear and suitable for adolescents.

The parent must see and edit the default instructions that control the writing. Each editable language-dependent configuration field must have independent Italian and English values. Changing the interface language selects the corresponding value; it neither translates nor overwrites the other value. The parent can develop the two versions independently.

This document starts with the requested renderer shortlist and defines the implementation order. The recommendation is provisional until a document prototype passes the checks below. No production renderer, model prompt, dependency or configuration is changed by this planning step.

## Implementation before the laboratory

[PageMaker.asked_for](../agents/page_maker.py) asks the image model to draw the whole sheet and letter its title, note and labels. [Page](../shared/page.py) permits at most four note lines of 72 characters each. A renderer replacement alone would preserve that restricted explanation: the content contract also needs to change. Some comments in the page contract still describe an older composed layout; the active page-maker implementation decides what happens now.

[printing/paper.py](../printing/paper.py) creates a single-page A4 PDF containing one raster image. Putting that same image into a different PDF library would leave the text problem unchanged. The new path must carry text strings through composition and preserve the composed PDF for printing and download. Raster page previews can remain available for vision and the parent interface, but must not replace the PDF master.

The retired layout code in the attic is historical context, not an implementation decision. The new layout must preserve the appealing visual character of the sheets while making instructions readable. Restoring a fixed collection of labelled rectangles without a visual trial would not demonstrate that result.

## Renderer candidates

The following comparison describes documented capabilities and engineering tradeoffs. It does not report a local performance benchmark or a successful installation on the project's platforms.

| Typst | A trusted typesetting template consumes structured data and images, then the compiler produces a PDF. | It provides document typography, page layout, graphics and automatic text flow. The initial proposal made WeasyPrint the first candidate because this work combines Python integration with flowing prose and paged layout. The owner then requested a direct comparison with Typst before any application change. Both were installed and tested in the laboratory described below. ReportLab remains an alternative if precise worksheet graphics dominate the design. Chromium is a reserve if browser-specific layout is necessary. No production renderer has been selected.

All four can compose actual text with images. None writes a better explanation by itself. The language model supplies the words; the renderer determines their placement and pagination. The first proof must therefore examine both content and the resulting printed page.

## Document behavior

The content model separates the explanation, any ordered actions, illustrations, captions, labels and areas used for the activity. These are semantic elements, not model-generated coordinates. A trusted template composes them into a document. An illustration model produces visual assets; essential instructions, titles, captions, labels and numbers remain text owned by the document. Geometric elements that need accurate dimensions or labels should use the renderer's drawing facilities where appropriate.

The explanation says what to do first, what materials are needed when that is not obvious, how to use the accompanying material, and what to return when the activity expects a return. It uses direct verbs and concrete references. It stays consistent with the approved activity and the materials available in the household. It should not become longer merely because two pages are available, and it should not turn every activity into the same form or use a childish tone.

One page is appropriate when the explanation and useful working space fit comfortably. Two pages are appropriate when an illustrated working sheet needs its own space or the explanation would otherwise be crowded. In that case, a short instruction page followed by the working sheet is the first layout to test, not a rule for every activity. A continuous two-page document is also valid when the content calls for it. The pages must refer to each other consistently and belong to one hand-over.

The renderer measures the result. It must not force one page by shrinking type indefinitely or force two pages by cutting text. If content exceeds the two-page requirement, a bounded editorial revision can simplify the wording while preserving the task; an unresolved overflow stops delivery and exposes the failure. Font sizes, margins and working-space minima will be selected from rendered and printed samples, with their provenance recorded. The existing 3 mm margin is a printer-related assumption, not an adequate reading margin by itself.

## Independent language settings

Each parent-editable textual instruction gets an Italian default and an English default maintained as separate source text. Initial fields should cover the explanation's writing style and, if exposed, illustration guidance. Before extending the configuration, inspect the existing parent-editable instruction fields and apply the same language rule to relevant existing fields rather than adding a second competing settings area. Numeric limits and switches do not need duplicated values merely because their labels are translated.

For each language, store the parent's override separately from the shipped default and its version. The editor shows the actual effective text, initially the default, and lets the parent edit it. The parent can inspect the default and restore it for that language alone. A default update must not overwrite a saved override. An absent override selects that language's default, never the other language's customization. No translation call runs on language switching or saving.

Switching between Italian and English must preserve both saved values and unsaved edits, or explicitly ask before discarding an edit. Each save addresses one language so simultaneous edits cannot replace the other version. Existing unscoped customizations must be preserved in their known language; ambiguous legacy values need an explicit migration choice rather than silent duplication or translation.

The interface language selects the configuration editor's visible language. The document uses the activity's explicit output language. Each generation records its effective instruction text, language and version so a later interface switch cannot change an already prepared document. The two concepts must be tested separately. Editorial preferences remain subordinate to authentication, household isolation and content-screening rules.

## First prototype and acceptance

The smallest discriminating experiment is a document containing a short explanation as actual text, an illustration and enough working space to need a second page. An offline one-page fixture first established text extraction and accented characters in both engines. The owner subsequently authorized real model calls for at least ten comparative cases. Their generated content was cached and reused for both engines, so layout revisions did not repeat paid generation.

The prototype fails if text extraction loses instructions or accents, if a label is baked into the illustrative bitmap, if content overlaps or falls outside printable bounds, if a working area becomes unusable, or if it creates an unexplained blank or third page. A deliberately overlong fixture must trigger a visible failure rather than clipping. Extracted text alone does not establish visual legibility or comprehension; inspect rasterizations of every page and repeat the owner's paper trial.

Record the exact renderer and font versions, output page counts, PDF sizes, elapsed render time and installation requirements. Verify the supported Python range and the production Linux container separately from Windows ARM64 development. Prefer server-side composition so the hub receives a finished document and does not need another layout runtime; validate that placement against the actual print transport before integrating it.

Templates and assets are trusted application resources. Model output enters as escaped text and validated structured data, never as arbitrary HTML, CSS, Typst source or Python. Resource loading must be limited to the document's supplied assets and fonts. Network access, arbitrary local-file reads and unbounded rendering must be prevented. The image instruction to omit lettering is not a guarantee; samples and later quality checks must detect unwanted generated text.

Two PDF pages do not imply automatic duplex printing. The physical test must establish whether separate sheets or supported duplex output serves the activity. Store previews rendered from the exact PDF master for matching and parent inspection. Preserve the printed document's version when language settings change, and preserve old single-sheet references for activities already open.

## Laboratory result on 19 September 2026

The local output directory is `experiments/17-pdf-layout-comparison`, with an overview in `README.md`. The combined `comparison.pdf` shows matching pages side by side. The `REPORT.md` records ten completed pairs, five in each language, with identical frozen source text and illustrations. These reports and generated binaries follow the existing experiment ignore policy and were not committed.

WeasyPrint 70.0 with Pango 1.58.2 and the Typst 0.15.0 Python binding ran in an isolated CPython 3.13.13 x64 environment on Windows ARM64. The final batch produced twenty PDFs with two A4 pages each. Text extraction retained the selected instructions, accents and symbols. Fonts were embedded; geometric checks found no text outside the page, overlapping text spans, text intersecting images or horizontal rules crossing text. The final local median rendering times were 0.243 s for WeasyPrint and 0.168 s for Typst, excluding imports, generation and inspection. The ordering was fixed and the sample small, so this is not a general performance benchmark.

The active text generation path was called unchanged. The laboratory composed its existing screen lines and page notes without rewriting them. The image request was explicitly adapted to request only the illustration; both its actual prompt and the unsent active whole-sheet reference were retained. Two text responses remained refused by the app's display-line limit and were marked as laboratory-only material; their printed words passed an independent safety check. One image case was refused twice by the unchanged Content Safety gate and replaced with an independently generated case. The failed evidence remains available.

The initial layout produced third pages in four WeasyPrint cases and three Typst cases. The retained baseline demonstrates the failure. Moving dense response fields into two columns and putting illustrations with the instruction page removed those third pages without shrinking text or dropping fields. Some second pages remain sparse, and narrower response fields need a physical usability trial. A separate overflow fixture remains over the limit and is detected rather than clipped.

The visual review found content defects shared by both engines: missing associations between image objects and text labels, unexpected raster lettering, and a garden grid that does not appear to match the requested dimensions. The existing display text also remains too compressed to demonstrate the requested standalone explanation. Both renderers remain viable; the next work is parent review followed by a content contract that carries explanations and explicit visual labels. No application integration is authorized by completion of this laboratory.
