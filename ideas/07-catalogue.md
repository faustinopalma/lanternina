# The catalogue: experiences designed once, for every house

An experience is a game, an activity, a thing to do — designed centrally, approved twice by
an administrator, offered to a parent by the household's own agent, and only then reaching
the adolescent. The design cost is paid once instead of once per family; the cost of
running it stays where it is.

Nothing here is built. The order below is the order in which it should be, and the first
entry is deliberately not the agent.

---

## 1. The vocabulary of capabilities, and the shape of a blueprint

**What it is.** Two contracts. The first names what a house can do — print A4, show 800x480
in one bit, scan a page, photograph the table — so that a blueprint can require some of them
and use others if present. The second is the blueprint itself: what a designed experience
*is*, in a form a machine can run and a person can read in full.

**Why it comes first, before any agent.** The blueprint decides whether the whole thing is
buildable. If the second level of detail produces code, then an agent writes programs that
run in other people's homes and an administrator approves them by reading prose — a
signature on something that was not read. If it produces **data over a closed vocabulary of
verbs**, the administrator approves something that can be read to the end.

The verbs we already have: print a sheet described by `SheetSpec`, show this on a display,
scan and read the cells, ask a model with this schema. A new verb is written by a person,
which is what keeps `orchestrator/safety.py` the single place content passes through.

**Where it starts.** `panel/devices.py` already holds the inventory — `display`, `printer`,
`scanner`, each with a job the parent assigns. The capability vocabulary is the same list
seen from the other side, and belongs in `shared/`. Then write **two experiences by hand**,
in the new format, using the two devices that exist.

**Done when.** Two hand-written blueprints run end to end on real paper and a real display,
with nothing generated by a model. If the format cannot carry two experiences a person
wrote, a model filling it would produce something plausible that nobody can execute — and
we would find out after building four approval gates around it.

**What it costs.** An afternoon, and it removes the risk of throwing away the large work.

---

## 2. The central agent, and the two administrator gates

**What it is.** An agent that knows the objects a house may contain and proposes
experiences: first a description a person can judge, then — once admitted — the blueprint
in full.

**What it must not receive.** A household. Not an identifier, not a preference, not what
came back on a sheet. The house may adapt on what it observes; the centre may not, or an
observation about a person leaves the home and accumulates in the one place that holds every
family. If a return path is ever needed, it goes through a person, not a pipe.

**The two gates only pay if they ask different questions.** The first is *is this a good
idea, and does it look like us*; the second is *is this realisation correct and safe*. The
way to tell they have collapsed into one: count how often the second gate changes the
outcome. If it never does, it is not filtering, it is only adding days between an idea and
a child.

**Approval must not start work.** It records a decision and stops, as every write in the
parent's panel already does. The reason here is also cost: admitting ten experiences would
otherwise start ten expensive elaborations at once. The `worker` container app already
scales on a queue and is the place for the work itself.

**Where it starts.** `shared/agents.py` — a new protocol beside `ContentAgent`, returning a
`Proposal` like every other agent, because a proposal has nowhere to record that it is
acceptable. The admission routes exist: `/api/admin/*`, in `panel/app.py`.

**Done when.** An administrator admits a description, asks for the detail in a second
action, and the blueprint that comes back is the one they then release — with the version,
the author and both decisions in the record.

**What it costs.** Tokens, centrally, and they are the point: paid once per experience
rather than once per family.

## 3. Versions, retirement, and what a parent actually approved

**What it is.** A parent approves a version, not a title. A revision is a new offer, not a
silent update; a house keeps running what it approved until somebody approves the next one.

**Why it is not a detail.** Without it the parent's approval means nothing after the first
revision, and the chain of consent this project is built on is broken in the one place where
it is invisible.

**Retirement is the other half.** An administrator must be able to withdraw an experience.
The ordinary case stops new activations and lets what is running finish; a withdrawal for
safety is a different, louder thing and should be a separate action, not the same one used
harder.

**A blueprint should arrive sealed.** `shared/seal.py` protects what leaves the house and
comes back approved. The catalogue is a new path *toward* the house, so the home server
should be able to prove that what it is about to run is what the administrator released.

**Done when.** A house running version 1 stays on version 1 after version 2 is released,
and says so; and a home server refuses a blueprint whose seal does not verify.

---

## 4. The household agent: selection, not creation

**What it is.** The agent in the home reads the catalogue, keeps what this house can
actually do, fills in the parameters from the household's settings, and offers the result to
the parent.

**Why it is cheap.** It creates nothing. The expensive generative work stayed central; this
one matches capabilities and fills fields that already exist in `panel/preferences.py` —
interests, things to avoid, difficulty, variety, words per line, language. Exactly the
fields `prompt_hints()` lets out of the house, and no others.

**What it must not do.** Offer what the house cannot run. An experience needing a printer
must be invisible to a house without one: offering it and then failing is worse than never
offering it, because the parent spends their own effort working out whose fault it is.

**And what the catalogue must not become.** No ordering by popularity, no adoption count, no
"most used". That is an engagement metric wearing the costume of a useful feature. Order by
what the house can do, and by date.

**Done when.** Two houses with different equipment are offered different catalogues, and
neither is offered something it cannot run.

---

## 5. Objects still to be conceived

One rule before the list: **a camera frames the paper, never the person.** It is the first
thing an agent would propose, and it is forbidden as an intermediate step too. The blueprint
must be able to say "photograph the table" and must have no way to say anything else.

- **A button.** It reverses the direction: the system does not call, the adolescent asks.
  It is the only object that makes starting their own decision, and the firmware already
  handles a press.
- **A speaker**, for reading aloud — already `05 §7`, waiting on a decision that is not
  technical.
- **A lamp.** One bit of state in the room, which does not call and does not blink. Useful
  precisely because it can be ignored.
- **Table material**: cards, dice, printed boards. The game lives between people and the
  system only supplies the paper. The category where we do least harm and help most.
- **A second display in a shared room**, as an object between parent and adolescent rather
  than a personal one.

**What the catalogue must not become, again.** A hundred mediocre experiences are worse than
eight good ones, because the parent's work turns into sorting — and the parent is the point,
not a queue to fill. A cap on the catalogue, and the discipline of retiring one before
adding one.
